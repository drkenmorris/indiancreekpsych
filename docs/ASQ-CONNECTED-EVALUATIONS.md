# Connected ASQ / ASEQ clinician evaluations

Returned questionnaires now open a protected clinician evaluation directly from the assignment row. The central patient record links to `/emr/asq?patient=<central UUID>`, which lists only that clinician's assignments for that patient and their response/evaluation status. The response review remains bound to the original assignment, respondent version and central patient; no name matching, browser QA import, or automatic combination of informants occurs.

The connected evaluator requires a complete submitted response. The server loads the immutable assigned definition and answers, validates the canonical source hash against the supported adapter, and calculates domain counts, raw sums, 0–4 endorsement means, frequencies for every answer option, and the original items reported Often / Almost always. Student domain metadata comes from the assigned Self bank, Parent from the actual parentItems construct metadata, Teacher from the assigned Teacher bank. All answers, including 0 and 4, are included.

These are descriptive response summaries. Existing QA helpers contain inconsistent 0–3/0–4 assumptions and unvalidated severity bands, so their diagnostic/severity interpretation is not promoted into connected records. No reverse keys are guessed from positive/negative wording; current published source banks do not define those keys. Mixed strength/difficulty wording is preserved for clinician review. The report explicitly states that raw endorsement means are not normed severity, diagnostic cutoffs, or a diagnosis. The clinician records interpretation and follow-up in the connected UI.

`asq_assignment_evaluations` stores append-only evaluation revisions with actor/time, submitted response revision FK, original definition hash, evaluation algorithm hash, generated report, clinician notes and a canonical snapshot hash. Updates/deletes are unavailable to authenticated clients. The assigning verified MFA administrator alone can read/write evaluations; respondents and other administrators cannot. SQL source/count bindings and expected-revision transaction locking prevent stale or cross-assignment writes. The API derives the report from stored responses and ignores client-provided report/patient claims. SQL stores clinician-authored content, not a digital clinical signature.

Reopening verifies snapshot integrity and reproduces the current report against the original answers before displaying it. A mismatched original version/adapter is blocked without rewriting either source or report. Old clinician interpretations remain in evaluation history. Current source can be versioned with `node scripts/version-asq-evaluation.mjs`; it hashes the evaluator, banks and recipient-source manifest. Never silently reinterpret an existing evaluation under a changed algorithm.

The old `/clinical-tests/asq` session QA workspace remains separate. Its assignment/results link now leads to the connected workflow; real returned answers are never copied into browser session stores. Invitations, respondent-only UI, seven-question saving, source definitions, existing scoring/narrative code, login/MFA and other instrument release flags are unchanged.

Verification must use fictional assignments and preserve actual patient records. Tests cover all three versions, 0/4 values, source/version integrity, server-built reports, explicit submitted-revision requirements, notes save/reopen/failure, clinician-only RLS, immutable history and optimistic conflicts. Live deployment verification uses the prior fictional submitted Teacher assignment only; do not open unrelated real questionnaire responses to test this feature.
